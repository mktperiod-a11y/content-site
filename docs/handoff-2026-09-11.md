### `0b0cb2c` — 상영 정보가 이틀에 한 번만 수집되던 버그

`last_success_at` 은 수집이 **끝난** 시각이라 크론이 뜬 시각보다 항상 뒤다.
그런데 잠금 조건이 TTL 을 정확히 24시간으로 쟀다. 크론이 매일 T 에 뜨고
수집이 45초 걸리면:

| | 임계값 | `last_success_at` | 결과 |
|---|---|---|---|
| 1일차 T | — | NULL | 획득 → `T+45s` 기록 |
| 2일차 T | `T` | `T+45s` | **튕김** |
| 3일차 T | `T+24h` | `T+45s` | 획득 |
| 4일차 T | `T+48h` | `T+48h+45s` | **튕김** |

→ 격일 수집. 게다가 조회 쪽 신선도 기준이 `INTERVAL * 2` = 48시간이라
**한 번만 실패해도 즉시 48시간을 넘겨 극장 딱지가 전부 사라진다.**

잠금 획득 조건에만 1시간 여유(`SYNC_SLACK_MS`)를 뒀다. 극장(24h)·개봉(7d)
양쪽 적용. 화면에 노출되는 `stale` 판정 기준은 그대로.

   > `getConfirmedTheatersByTitle(rows.map((r) => r.title_ko))` 를 되살리고

### `백오프` — 실패한 수집을 방문자마다 재시도하던 문제

수집이 실패하면 `lock_until = 0` 으로 잠금을 즉시 풀었다. 그런데 실패했으니
`last_success_at` 은 그대로라 `stale` 이 계속 true 고, 그러면 `ReleaseRefresh`
가 **누가 페이지를 열 때마다** `/api/releases/refresh` 를 자동 POST 한다.
→ 방문자 수만큼 외부 API 재시도. 상대가 장애일 때 우리가 부하를 더 얹는 구조다.

API 키가 없는 지금 이미 이 상태였고, 키를 넣어도 KOBIS 일시 장애 때 같은 일이
벌어진다.

실패 시 `lock_until` 을 `실패시각 + 10분` 으로 잡는다. `acquireLock` 이 이미
`lock_until < now` 를 보고 있어서 재시도가 자동으로 막힌다.

- 스키마 변경 없음 (기존 `lock_until` 컬럼 재사용)
- 성공 경로 변화 없음, 화면 변화 없음
- 쿨다운(10분)이 수집 주기(24시간/7일)보다 훨씬 짧아 정상 갱신을 늦추지 않는다

**동작 확인:** 갱신이 3일 지난 상태로 두고 `/api/releases/refresh` 를 두 번 쳤다.

```
1차 → source_error (HTTP 403), status='error', lock_until = +600초
2차 → fresh_or_running   ← 재시도 차단됨
```

### `SEO` — robots.txt 부재 · 링크 미리보기 없음

검색 유입이 목표인데 기본 세 가지가 비어 있었다. 전부 메타데이터라 화면 변화는 없다.

- **`robots.txt` 가 아예 없었다.** 크롤러가 사이트맵을 찾아갈 경로가 없었다.
  `app/robots.txt/route.ts` 추가 (기존 `sitemap.xml/route.ts` 와 같은 방식).
  `/search` 는 이미 noindex 라 크롤링에서 빼고, `/api/` 도 막았다 — 크롤러가
  부를 이유가 없고 부르면 외부 API 쿼터만 소모한다.
- **`metadataBase` 가 없었다.** 하위 페이지가 상대 경로로 canonical·og:url 을
  써도 절대 주소로 안 풀렸다.
- **Open Graph / Twitter 카드가 없었다.** 링크를 공유하면 미리보기가 안 떴다.
  루트에 한 번 넣으면 하위 페이지가 각자의 title/description 을 물려받는다.

주소는 `lib/site.ts` 의 `getSiteUrl()` 로 모아, 사이트맵·robots·메타데이터가
같은 값을 쓰게 했다 (`PUBLIC_SITE_URL` 우선, 없으면 상수).

> 남은 것: 페이지별 `alternates.canonical`. `metadataBase` 가 들어갔으니
> 상대 경로로 한 줄씩 붙이면 된다. 프로덕션 도메인 확정 후 하는 게 안전하다.
> OG 이미지(`og:image`)도 아직 없다 — 있으면 공유 시 카드가 훨씬 눈에 띈다.

## 3. 남은 과제

### 🟡 검토 필요 (결론 못 냄)

- **극장 3사 약관·robots.txt 검토** — 세 곳 모두 공식 공개 API 가 아니라
  각 사이트가 자기 화면을 그릴 때 쓰는 내부 JSON 엔드포인트다. HTML 크롤링은
  아니지만 문서화된 용도는 아니다. robots.txt 보다 **이용약관의 자동화 접근 조항**
  이 실질적으로 중요하다. 법무 판단 영역.
- **Cloudflare Worker IP 차단 여부** — 미검증. 배포 후 크론이 한 번 돈 뒤
  아래로 확인하면 된다. 별도 계측 코드는 필요 없다.

```sql
SELECT sync_key, status, last_error, last_success_at FROM sync_state
WHERE sync_key LIKE 'theater:%';
SELECT theater_code, COUNT(*) FROM theater_movies GROUP BY theater_code;
```

`status = 'idle'` 이고 극장사별 60~80편이면 정상. `error` 면 `last_error` 에 이유.

### 🔴 배포 후 조치 필요 — 외부 API 쿼터 보호

인증도 레이트리밋도 없이 외부 API를 증폭 호출하는 경로가 둘 있다.

```
GET  /api/movies/search?q=X   →  KOBIS 최대 6회 (제목·감독 + 단어 경계 조합)
POST /api/movies/enrich       →  TMDB  최대 24회 (작품 12개 × 매칭+제공처)
```

요청 1번에 외부 호출 6~24번이다. 인메모리 캐시는 같은 검색어를 10분간만
막고, 검색어를 바꾸면 그대로 뚫린다. **KOBIS 는 일일 쿼터가 있어서**,
스크립트로 검색어를 돌리면 하루치가 소진되고 사이트 검색이 통째로 죽는다.

키가 없는 지금은 드러나지 않지만 **키를 넣는 순간 열린다.**

코드로 막기보다 Cloudflare Rate Limiting Rules 로 IP당 제한을 거는 게 맞다.
`buildKobisSearchPlans` 의 조합 수를 줄이면 호출은 1/3로 주는데 검색 품질이
떨어져서 권하지 않는다.

### 🟢 제안 (지시 없어 손대지 않음)

- **예매율 순 정렬** — 세 API 모두 예매 지표를 준다 (CGV `atktRate`,
  메가박스 `boxoRank`, 롯데 `BookingRate`). 지금의 "극장사 수" 정렬보다
  정확하지만 `theater_movies` 컬럼 추가 + 마이그레이션 + 파서 3곳 수정이 든다.
- **`개봉 예정작` 을 KOBIS 없이 채우기** — 극장 3사에 개봉예정 엔드포인트가
  있다 (CGV 상영예정 탭, 롯데 `moviePlayYN=N`, 메가박스 `rfilmDe` 미래분).
  API 키를 넣으면 불필요해지는 작업이라 보류.
- `lib/ott-plans.ts` 월 요금 실검증 (`PRICES_VERIFIED_ON = "2026-09-04"`) —
  공개 배포 전 필수.
- `theater_titles` CTE 에 신선도 필터 없음. 의도된 동작으로 보이나
  (수집 실패 시 기존 목록 유지), 스냅샷이 낡으면 목록엔 남고 칩만 사라지는
  조합이 나온다. 그대로 둘지 판단 필요.
- `/` 307 리다이렉트 유지, KMDb 연동 미착수.

## 4. 작업 환경 제약 (검증 범위 한계)

이 작업은 아웃바운드가 차단된 환경에서 진행됐다. `kobis.or.kr`,
`api.themoviedb.org`, 극장 3사, `cdn.jsdelivr.net`, 배포 사이트 전부 접근 불가.

그래서 저장소의 마이그레이션으로 **같은 스키마의 인메모리 DB** 를 만들고
조사 문서에 기록된 실제 제목 표기(CGV 의 하이픈 표기 포함)를 넣어 검증했다.

| 검증됨 | 검증 안 됨 |
|---|---|
| SQL·정렬 로직 | 극장 3사 엔드포인트 생존 여부 |
| 제목 정규화가 3사 표기를 묶는지 | 실제 제목 표기가 조사 시점과 같은지 |
| 레이아웃·반응형 (360~1536px) | 실제 편수 |
| 수집 실패 시 기존 데이터 보존 | Pretendard 실제 렌더 |

**로직은 확인됐지만 외부 데이터 유입은 배포 후에만 알 수 있다.**
